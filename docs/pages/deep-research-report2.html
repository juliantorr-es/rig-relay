Rig Relay audit of the context-caching assessment

Bottom line

I audited the code in the urlrig-relay repositoryturn2view0, focusing on `vibe/core/context/assembler.py`, `vibe/core/telemetry/context_blocks.py`, `artifacts.py`, `manifest.py`, `send.py`, and the README. My judgment is that your audit is **mostly directionally correct**, but it is **not fully accurate as written**. The repo clearly does implement deterministic context layout, exact SHA256-based prefix fingerprints, prefix-stability reporting, and optimization hints. It also clearly persists full JSON reports per session and does not show an inspected cross-session block pool or delta format. But two parts of the gap analysis are too strong: project-local evidence is **supported** rather than universally assumed, and the repo already contains an **evidence-manifest mechanism** with relative-path hashing, plus durable artifact writes with `fsync`. What I could not confirm from the inspected call sites is whether that manifest machinery is always invoked on every runtime path. citeturn10view0turn11view0turn21view0turn22view0turn45view0turn35view1

What is clearly accurate

The strongest part of your write-up is the claim that Rig Relay is intentionally engineering a deterministic reusable prefix. In `plan_context_layout`, blocks are sorted by stability class in the order **stable → semi-stable → dynamic → ephemeral**, with tie-breakers on block kind, source index, fingerprint, and byte size. The stable prefix is then defined as cacheable stable and semi-stable blocks. In `build_context_assembly_report`, system messages are emitted as `SYSTEM_PROMPT`, optional tool schema metadata is emitted as `TOOL_SCHEMA`, and `classify_block_stability` marks those kinds as stable and cacheable. That is solid evidence for a deterministic prefixing strategy designed to make exact-prefix reuse more likely. citeturn10view0turn12view0turn17view0

Your fingerprinting point is also correct. The repo uses exact SHA256 hashes, not fuzzy semantic matching: `fingerprint_text` returns a SHA256 digest, the layout plan computes stable-prefix and dynamic-suffix fingerprints from ordered block fingerprints, and `prefix_stability_status` becomes `"stable"` or `"changed"` by comparing the current stable-prefix fingerprint with the previous layout’s fingerprint. That is exactly the kind of exact-match reuse check you described. The only nuance is that your wording blurs two artifacts together: `cacheability_ratio` and `prefix_stability_status` live on `ContextLayoutPlan`, while the assembly report itself carries `cache_candidate_bytes` and `optimization_hints` but not the ratio field. citeturn17view0turn11view0turn12view0

What the audit understates

The repo is a bit **ahead** of your write-up on artifacting. `artifacts.py` already contains explicit tool-result artifacting primitives: it artifacts content above `16384` bytes, creates a bounded prompt excerpt of at most `4096` bytes with a `[TRUNCATED]` marker, and writes a self-describing JSON artifact as the authoritative local record. On the context side, the assembler checks for `[TRUNCATED]` in tool content and classifies that content as an `ARTIFACT_REFERENCE` block. So Rig Relay is not only *hinting* that large tool results should be artifacted; the codebase already contains artifact-aware context plumbing. I cannot prove from the inspected files alone that every runtime path is wired to use it, but the capability is clearly present in the repository. citeturn44view0turn45view0turn12view0

What is partly right but needs correction

Your privacy and security warning is real, but it needs tighter wording. The assembly report stores raw block `content`, `_make_block` fingerprints and sizes that content, and `write_assembly_report` serializes the whole report to JSON. The artifact envelope also records raw tool output in the payload and stores `metadata.path` as `str(artifact_path)`, while the telemetry client publishes both `artifact_path` and `layout_path` fields. In the inspected context and telemetry files, I did not find `redact` or `sanitize` logic. That said, “project-local evidence” is too broad: the README says the default home directory is `~/.rig/relay/`, while `./.rig/relay/` is a supported project-local root rather than the universal default. So the corrected claim is: **raw content and absolute paths can be persisted, and that can become project-local depending on configuration or root resolution, but it is not always project-local by default**. citeturn12view0turn45view0turn28view2turn46view0turn46view1turn46view2turn46view3turn35view1

The biggest factual miss in the original audit is the statement that Rig Relay has no integrity monitor or evidence manifest. `manifest.py` defines an evidence-manifest schema, records **relative paths** and SHA256 hashes for observability logs, tool artifacts, and context reports, and can write and load `manifest.json`. On top of that, the artifact writer uses atomic replace plus `fsync` on both the file and the parent directory. The more accurate criticism is narrower: I did not verify from the inspected call sites that `write_session_manifest` is always invoked, and the assembly/layout/shadow writers themselves use atomic replace without the same explicit `fsync` durability step that artifact writes have. So the repo’s state is **“integrity machinery exists, but runtime coverage and durability are uneven,”** not **“there is no integrity machinery.”** citeturn21view0turn22view0turn45view0turn11view0turn12view0

What still looks like a real gap

The “single-tier / no local block pool” criticism is substantially fair based on the code I inspected. `load_latest_layout` only reads prior layout JSON for the **same** `session_id` under `SESSIONS_ROOT / session_id / context`, artifact storage is also rooted under `SESSIONS_ROOT / session_id`, and each `ContextBlock` gets a fresh UUID `block_id` while still carrying full `content`. That is a session-scoped, disk-backed design. I did not find evidence in these inspected modules of a repo-level, content-addressed stable-block store or any cross-session deduplication layer. citeturn11view0turn17view0turn44view0

The write-amplification point is also substantially correct. `write_assembly_report`, `write_layout_plan`, and `write_shadow_request_report` each serialize the full model to canonical JSON, and the assembly report contains the full `blocks` list, with each block carrying `content`. I did not find a patch, delta, or compact binary representation in the inspected context path. So if the same stable prompt or tool schema appears across many turns, the current mechanism will keep re-emitting that material in successive assembly artifacts unless some higher-level runtime path suppresses report creation. citeturn12view0turn11view0turn17view0

One more caution: the “Level 4 maturity” or “maximizing provider-side KV cache hits” language is somewhat stronger than what the code proves. The repo absolutely demonstrates **cache-friendly context engineering** and even emits a hint that a changed stable prefix may lose a provider cache hit. But in the telemetry client I inspected, I did not find provider-cache-hit, provider-KV-cache, or similar runtime verification signals. In other words, the code shows strong **prefix-stability instrumentation**, not direct measurement of actual provider-side cache efficacy. citeturn10view0turn11view0turn43view0turn43view1turn43view2

Corrected judgment

If I rewrote your audit in one sentence, I would call it **mostly accurate on deterministic prefix engineering, exact-fingerprint drift detection, snapshot-based persistence, and the lack of an inspected multi-tier cache**, but **partly inaccurate on artifacting maturity, default storage locality, and the claim that no evidence-manifest or integrity mechanism exists**. The highest-value corrections are still the same in spirit, though: add redaction and path-normalization at the artifact and telemetry boundaries, then move toward content-addressed dedupe and delta-style report storage, and then add provider-aware cache observability so you can measure real reuse rather than infer it from prefix stability alone. citeturn45view0turn28view2turn21view0turn22view0turn11view0turn12view0turn43view0
