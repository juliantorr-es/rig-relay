Coordination Event Ledger Contract v1

The Coordination Event Ledger Contract v1 formalizes how Rig Relay records audit-discovered contract seams, proof-chain gaps, fake-green tests, and unverifiable release blockers as structured, schema-governed coordination events. The ledger uses append-only JSONL storage under the existing coordination infrastructure with flock-based write protection and content-light path hashing.

Purpose

Two independent read-only audit lanes found that Rig Relay has many strong contract surfaces, but the open release blockers are largely unverifiable because several enforcement tests validate blocker description text rather than implementation evidence. The 14 deduplicated seams span CI/CD, release gate validation, MCP, ACP, SDK, A2A, telemetry/redaction, local API envelope, and coordination. The Coordination Event Ledger Contract v1 gives Rig a canonical vocabulary for recording these seams so future slices (CI Evidence Contract v1) can consume them rather than invent new proof substrates.

Seam Event Vocabulary

Seam events record a discovered gap in a contract surface. Each seam event carries: event_kind, contract_family_id, seam_class, severity, proof_chain_status, fake_green_risk, and hashed references to affected files, evidence files, schemas, implementations, validators, and tests. The seam_class enum covers 15 classification types including schema_authority_missing, producer_missing, consumer_missing, validator_theater_detected, release_blocker_unverifiable, and fake_green_test_detected. The event_kind enum covers 18 event types including contract_seam_discovered, proof_chain_incomplete, and contract_family_promoted/deferred.

Schema authority: docs/schemas/rig.relay.coordination.seam_event.v1.schema.json

Proof-Chain Event Format

Proof-chain events record the completeness of a contract surface's proof chain: which authority, schema, producer, consumer, validator, test, and evidence files are present or missing. Four boolean flags track missing validation dimensions: schema validation, artifact hash validation, trace/correlation validation, and telemetry/redaction validation. The proof_chain_status enum uses complete, partial, theatrical, and missing. Schema authority: docs/schemas/rig.relay.coordination.proof_chain_event.v1.schema.json

Fake-Green Event Format

Fake-green events record enforcement tests that pass but validate description text rather than implementation evidence. Each event carries: test_file_hash, test_function, fake_green_pattern (9 patterns including blocker_text_only_enforcement, file_existence_only, schema_not_loaded, and producer_is_only_consumer), why_theatrical, what_would_still_pass_description, and missing_adversarial_test_description. Schema authority: docs/schemas/rig.relay.coordination.fake_green_event.v1.schema.json

Content-Light Path Hashing Rule

All file path references in seam, proof-chain, and fake-green payloads use salted SHA256 hashes via salted_path_hash() from rig_relay/coordination/models.py. Raw file paths must never appear in event payloads. The salt is cryptographically random per process, ensuring export-safe hashes. This rule applies to: affected_file_hashes, evidence_file_hashes, schema_file_hashes, implementation_file_hashes, validator_file_hashes, test_file_hashes, authority_file_hashes, producer_file_hashes, consumer_file_hashes, and test_file_hash.

Payload Builder API

Four new payload builder functions in rig_relay/coordination/models.py produce content-light payloads for the new event types. All builders use keyword-only arguments, require critical fields explicitly, produce deterministic event_ids from canonical JSON content hashes, and never store raw file paths.

  • build_seam_discovered_payload(contract_family_id, seam_class, severity, proof_chain_status, fake_green_risk, affected_file_hashes, ...) -> dict: Produces a seam event payload with schema_version rig.relay.coordination.seam_event.v1.
  • build_proof_chain_incomplete_payload(surface_id, contract_family_id, proof_chain_status, ...) -> dict: Produces a proof-chain event payload with schema_version rig.relay.coordination.proof_chain_event.v1.
  • build_fake_green_test_detected_payload(contract_family_id, test_file_hash, test_function, fake_green_pattern, why_theatrical, what_would_still_pass_description, missing_adversarial_test_description, ...) -> dict: Produces a fake-green event payload with schema_version rig.relay.coordination.fake_green_event.v1.
  • build_release_blocker_unverifiable_payload(contract_family_id, blocker_id, seam_class, severity, proof_chain_status, fake_green_risk, affected_file_hashes, ...) -> dict: Produces a seam event payload (same schema) specialized for release blocker unverifiability.

File Coordination Schema

The file coordination marker protocol declared by file_markers.py now has a canonical schema at docs/schemas/rig.file_coordination.v1.schema.json. The schema defines a content-light marker object with schema_version, protocol, session_id, task_id, claim_kind, marker_sha256, and created_at.

Missing EventName Registrations

Two missing EventName members were registered in rig_relay/core/telemetry/constants.py: COORD_TASK_CLAIM_REFUSED = coord.task.claim_refused and RELEASE_BUNDLE_BUILT = rig.relay.release.bundle_built.

OTel and OpenCode Telemetry Boundary

OTel observes. Rig governs. The coordination ledger remembers. CI proves later. The OpenCode telemetry plugin is installed for live observation, but Rig's ledger must first define the canonical seam/proof-chain event vocabulary. OTel adapter ingestion is a future slice. OpenTelemetry context propagation is useful for correlating traces, metrics, and logs across process/service boundaries, but this slice stays focused on Rig's own canonical JSON/JSONL event contract. The coordination ledger is the source of truth for contract seam events; OTel data will be consumed as future adapter input, not as canonical Rig truth.

CI Evidence Contract v1 Consumption Path

CI Evidence Contract v1 is the next implementation slice. It will consume seam/proof-chain/fake-green events from the coordination ledger rather than inventing its own proof substrate. The CI surface will read the ledger's seam events to know which contract surfaces need CI-produced structured evidence, which release blockers are unverifiable without CI artifacts, and which tests are fake-green and need adversarial hardening. This layered architecture means CI evidence does not need to re-discover seams that the audit lanes already found.

Test Coverage

Three test files validate the contract: test_seam_event_vocabulary.py (contract/real-artifact/adversarial), test_proof_chain_events.py (contract/real-artifact), and test_coordination_real_artifact.py (real-artifact/adversarial/concurrency/substrate). Tests prove: all seam event kinds validate, all seam_class values accepted, missing required fields rejected, invalid enums rejected, raw paths absent from payloads, schema_version resolves to existing schemas, EventName contains new members, 14 audit seams normalize to valid events, fake-green requires critical fields, proof-chain rejects impossible statuses, payload builders validate against declared schemas, real JSONL ledger writes validate, ledger integrity passes, malformed JSONL detected, duplicate event_id detected, and concurrent writes do not corrupt.

Dependency Doctrine

No new dependencies were added. The ledger contract uses existing infrastructure: salted_path_hash, dump_canonical_json, CoordinationEvent model, check_ledger_integrity, flock-based digester locks, and append-only JSONL storage. DuckDB is not used as mutation authority, lease authority, consent store, or transaction engine in this slice. SQLite was not added. The contract is fully compatible with the existing coordination store infrastructure.
