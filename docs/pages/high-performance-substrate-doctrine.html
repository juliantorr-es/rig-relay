High-Performance Substrate Doctrine

Source-of-Truth Hierarchy

Rig Relay's data architecture follows a strict hierarchy. Each layer has a defined role and cannot usurp the authority of the layer above it.

  • JSON/JSONL/CSV — canonical evidence and source-of-truth artifacts. Portable, inspectable, diffable, replayable, schema-governed. All other layers are downstream projections.
  • PostgreSQL — enterprise operational substrate. Owns operational queryability, projection invalidation, audit/event correlation, enterprise admin debuggability, and replay/export orchestration. JSONB inside PostgreSQL is schema-governed envelope representation, never an untyped dumping ground.
  • DuckDB — disposable analytical microscope. In-memory, read-side only. Reads JSONL/Parquet files for ad-hoc analytical queries. Never writes back to artifacts. Never a mutation authority.
  • Apache Parquet — derived analytical snapshot format. Generated via DuckDB COPY FORMAT PARQUET from canonical JSONL. Never canonical event truth. Always rebuildable from canonical artifacts.
  • Apache Arrow — transient in-memory columnar interchange format. Prototype behind ProjectionStorePort after PostgreSQL ports exist. Optional [arrow] extra. Never persisted as canonical artifact.
  • Zstandard — compression optimization. Already canonical dependency (zstandard>=0.25.0). Expands to session bundles, archive compaction, and export packages. Compression is storage optimization — never redaction, never privacy, never canonical authority.
  • Pydantic v2 / pydantic-core — typed model boundary. Rust-backed serialization and validation. Should be exploited at every module boundary before considering alternative serialization libraries.

Promoted Tools (Phase 1-3)

These tools are approved for implementation with zero new dependencies or with planned dependency additions at specific phases:

  • Apache Parquet (via DuckDB) — already in use via DuckDB COPY FORMAT PARQUET. Formalize derived snapshot doctrine with contract test. Zero new dependency.
  • psycopg 3 COPY / binary COPY — PostgreSQL bulk ingest/export with staging table + constraint promotion pattern. Dependency: psycopg[binary]>=3.2 at Phase 3 (Postgres Adapters). Never COPY directly to operational tables.
  • Zstandard (expanded usage) — already canonical dependency. Expand to session bundles, archive compaction, export packages. Zero new dependency.
  • Pydantic v2 (exploited harder) — replace stdlib json.loads/dumps at module boundaries with model_validate/model_dump_json. Extra='forbid' for content-light enforcement at type level. Zero new dependency.

Prototype Tool (Phase 3)

One tool is approved for prototyping behind a feature flag:

  • Apache Arrow / PyArrow — in-memory columnar interchange behind ProjectionStorePort. Optional [arrow] extra in pyproject.toml. Dependency: pyarrow>=19.0 at Phase 3 only. Arrow schema derived from Pydantic models. Arrow conversion failure falls back to dict-of-dicts. Never a hard dependency.

Parked Tools (Phases 4-7)

These tools are parked — no dependency may be added without measured bottleneck evidence and a satisfied gate condition:

  • ADBC / Arrow Flight — park. Premature before PostgreSQL ports exist. Audit later if hosted/team mode requires high-throughput Postgres-Arrow transport.
  • Polars — park. DuckDB already provides 95% of Polars' analytical capability. Evaluate only if Phase 4 equivalence tests reveal DuckDB-insufficient bottlenecks.
  • Ibis — park. Raw SQL with contract tests is clearer and more auditable for 2 backends (DuckDB + PostgreSQL). Ibis adds abstraction overhead at Rig Relay's scale.
  • Apache DataFusion — park. DuckDB dominates this need. DataFusion's Arrow-native architecture is interesting but adds complexity without measurable advantage.
  • pgvector — park. Phase 6 audit required. Gate: PostgreSQL operational substrate must exist, sensitive-derived-data policy must be defined, embedding model must be selected, local-only boundary must be enforced for private repo content.
  • pg_jsonschema — park. Phase 5 defense-in-depth. Gate: PostgreSQL operational substrate must exist, schema registry must be populated. Application-level jsonschema remains primary validation.
  • pgmq / SKIP LOCKED — park. SKIP LOCKED pattern on coordination_lease table may be useful for lease cleanup. Full pgmq is overkill. Do not turn PostgreSQL into an orchestration tar pit.
  • orjson — park. No measured JSON bottleneck in current workload. Evaluate only if Phase 1 measurement harness proves json.loads/json.dumps is a significant bottleneck. If adopted, must enforce no fast-path bypass of jsonschema/Pydantic validation.
  • SQLGlot — park. Phase 7 linting/validation tool. Useful for detecting DuckDB-specific SQL in portable projections and validating PostgreSQL migration SQL dialect correctness. Do not auto-transpile without equivalence tests.

Rejected Tools

  • msgspec — reject. Pydantic v2 + pydantic-core already provides Rust-backed serialization. msgspec duplicates the model layer without clear benefit.
  • Apache Iceberg / Delta Lake — reject. Wrong scale for local-first architecture. Designed for petabyte-scale data lakes with object storage. Parquet snapshots already sufficient.
  • LanceDB / separate vector stores — reject. Fragments PostgreSQL operational authority with a separate database. pgvector inside PostgreSQL is the preferred architecture if vector search is needed.
  • SQLite — reject. Explicitly forbidden by existing architecture policy. PostgreSQL replaces any need for an embedded database.

Content-Light Enforcement Continuity

Content-light enforcement must apply at every stage of the substrate pipeline. No tool may introduce raw content into a stage that previously guaranteed content-light. The enforcement chain:

  1. Application boundary: redaction.py scans all data before artifact write. 50 forbidden field keys. 5 pre-compiled regex patterns.
  2. Schema validation: jsonschema validates against docs/schemas/*.schema.json at ingestion boundary.
  3. Arrow schema: Arrow table schemas exclude forbidden field names. Arrow is never persisted as canonical artifact.
  4. Parquet column validation: Parquet column names validated against forbidden field patterns at generation time.
  5. PostgreSQL CHECK constraints + INSERT triggers: defense-in-depth on all JSONB columns. Staging table + constraint promotion for COPY imports.
  6. DuckDB views: duckdb queries select from content-light generated columns and materialized views only. Analyst role cannot query raw JSONB payloads.
  7. Cockpit/static docs/procurement output scans: all outputs scanned for raw content before display or publish.
  8. Zstandard bundles: decompressed data must pass redaction scan before use. Compression is storage optimization, not redaction bypass.

Roadmap Sequencing

The high-performance substrate roadmap runs in parallel with the PostgreSQL enterprise substrate migration. The ordering is enforced: no optimization before measurement, no new dependency before existing dependencies are exploited, no database-adjacent tool before ports exist.

  1. Phase 0 (current): Audit. No code changes. No dependencies.
  2. Phase 1: Measurement harness. Identify actual bottlenecks in JSONL parsing, DuckDB projections, static docs generation, procurement pack generation. Expand Zstandard and Pydantic — zero new dependencies.
  3. Phase 2: Port definition and file-backed reference adapters. Zero new dependencies.
  4. Phase 3: PostgreSQL adapters + psycopg COPY + Arrow prototype. Dependencies: psycopg[binary]>=3.2, optionally pyarrow>=19.0 as [arrow] extra.
  5. Phase 4: Replay equivalence tests. Zero new dependencies.
  6. Phase 5: Cockpit integration. pg_jsonschema parked (PostgreSQL extension, not Python dependency).
  7. Phase 6: Enterprise mode + pgvector audit. pgvector Python client only if promoted from park after sensitive-derived-data policy.
  8. Phase 7: Procurement documentation + SQLGlot linting. SQLGlot only if promoted from park.
  9. Phase 8: Re-evaluate parked candidates (Polars, Ibis, DataFusion, ADBC, Iceberg) based on measured bottlenecks.

Dependency Doctrine

No new dependency from the high-performance substrate audit is approved for immediate implementation beyond existing canonical dependencies. The following additions are approved only at the specified phases and gates:

  • psycopg[binary]>=3.2 — approved only at PostgreSQL Phase 3 when PostgreSQL adapters exist and staging table + constraint promotion doctrine is enforced.
  • pyarrow>=19.0 — optional/prototype-only behind [arrow] extra after ProjectionStorePort exists at Phase 3. Never a hard dependency.
  • orjson, Polars, Ibis, DataFusion, SQLGlot, pgvector, pg_jsonschema — remain parked until the specified gate condition is met and measured bottleneck evidence is provided.
  • msgspec, Iceberg/Delta, LanceDB, SQLite — rejected for current Rig Relay architecture. Re-evaluated only if architecture materially changes.

Required Tests

The following tests must exist (not necessarily pass) before any substrate tool is approved for production use. Each test is classified by type:

  • Parquet-never-canonical contract test (contract, real-artifact, adversarial)
  • Zstandard decompress-then-redact tests (contract, adversarial, substrate)
  • Pydantic extra='forbid' boundary tests (contract)
  • PostgreSQL COPY staging-table validation tests (contract, integration, adversarial, substrate)
  • Arrow/dict projection parity tests — only if Arrow prototype exists (contract, substrate)
  • pgvector sensitive-derived-data safety tests — only if pgvector promoted from park (adversarial, substrate)
  • No raw content across substrate seams (adversarial, sabotage)
  • Performance measurement baselines before any optimization (substrate)
  • Product telemetry disabled does not stop enterprise audit/evidence writes (contract, integration)
  • Content-light materialized views never contain raw content (adversarial)
  • Static docs output scan catches absolute paths/tokens/source snippets (adversarial)
