ToolRuntime Boundary

Purpose

Rig Relay separates concerns between AgentLoop (turn conductor), ToolRuntime (governed execution authority), Ralph (observe-only scanner), the desktop HITL boundary, and the analytics compiler. ToolRuntime owns the governed tool execution path.

Layered Execution Model

Desktop UI       Renders projections, sends intents. Dumb renderer.
Desktop Backend  Validates state, processes intents. Owns refusal codes.
Ralph            Scans projections, ranks candidates. Not an executor.
AgentLoop        Turn conductor — topology, middleware, session lifecycle.
ToolRuntime      Governed execution authority. Normalization, permission,
                 cache, gating, execution, receipt, refusal.
Analytics        Reads ledgers, compiles facts/projections. Never executes.

ToolRuntime Responsibilities

  • Tool call normalization and validation
  • Permission checks (ToolPermission: ALWAYS / ASK / NEVER)
  • Deterministic result cache (pure / repo-state tools)
  • Patch proposal gating for mutation tools
  • Tool execution via tool_instance.invoke()
  • Result normalization (success / failure / skipped)
  • Tool receipt emission (build_receipt)
  • Tool analytics event emission
  • Refusal normalization (ToolPermissionError to refusal receipt)

Ralph Is Not ToolRuntime

Ralph owns projection scanning, candidate ranking, mission candidate proposal, approval state and decision receipts. Ralph may submit bounded read-only missions to ToolRuntime through the desktop HITL boundary. Ralph must never execute tools directly, bypass permission gates, or mutate the workspace.

Desktop HITL Does Not Execute Tools

The desktop HITL boundary approves or declines mission candidates. Approval is a state transition, not an action trigger. Execution requires a separate contract through ToolRuntime.

Current Normal Flow

RuntimeToolExecutionRunner → validate envelope → lease check →
ToolRuntime.execute_one() → governed tool invocation →
ToolRuntimeResult → runtime audit event

Validation Gates

  • ToolRuntime execute_one() governs all execution paths
  • Span finalization verified on all 8 early-return paths
  • Supervisor result envelope propagated through ToolSubprocessResult
  • No silent except:pass in ToolRuntime critical paths
