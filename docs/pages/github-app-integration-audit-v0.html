observe_public_repo: Observe Public Repository

Read repository metadata and events for public repos. No write access.

Rationale: Minimum permissions required for event observation. Contents read is needed for reading repository files through the API. Checks read is needed for observing CI/check outputs. Issues read is needed for issue comment observation if used for agent collaboration.

Risks:

  • Contents read exposes repository source code to the Rig process
  • Event payloads may contain sensitive commit metadata
  • Scope creep if additional read permissions are requested later without profile audit

User consent copy: Rig Relay will observe repository events (pushes, pull requests, checks) to build local evidence. No code or repository content will be sent to external services. All processing is local.

evidence_status_reporter: Evidence Status Reporter

Post Rig status/check outputs back to GitHub after local validation. Adds write access for checks/statuses.

Rationale: Checks write allows creating annotated check runs. Commit statuses write allows posting status to PRs. Both are required for the evidence feedback loop: Rig validates locally, reports results to GitHub.

Risks:

  • Write access to checks/statuses could be misused to post misleading status
  • Check run annotations could expose local file paths or internal state
  • Need approval gate before any automated status posting

User consent copy: Rig Relay will post check runs and commit statuses to GitHub with validation results. No code or internal file paths will be included in status reports.

governed_pr_assistant: Governed Pull Request Assistant

Create branches, PRs, and comments only after explicit user approval. Highest-risk profile with write access.

Rationale: Contents write is required for branch/commit creation. Pull requests write for PR creation. Issues write for commenting on PRs/issues. All write actions are gated behind explicit user approval in the cockpit.

Risks:

  • Contents write is the highest-risk permission — allows pushing commits
  • Pull requests write could be misused to modify or close PRs
  • Requires robust approval UI and audit trail
  • Requires worktree isolation to prevent dirty-file corruption

User consent copy: Rig Relay may create branches, commits, and pull requests on your behalf. Every write action requires explicit approval in the desktop cockpit. You can review the full diff before approving. All actions are recorded in the local evidence store.

admin_avoidance_profile: Admin Avoidance Profile

Explicitly documents permissions Rig should NOT request for v0. Serves as a safety checklist.

Rationale: Administration, Secrets, Actions write, Workflows write, Deployments write, Repository rules write, and Organization members write must never be requested in v0. These permissions grant broad mutation authority that violates Rig's governed, approval-gated design. Pages/webhooks write could interfere with GitHub Pages publishing or webhook configuration. Security events read could expose vulnerability data.

Risks:

  • Accidental inclusion in permission manifest during implementation
  • Organization-level permissions could be requested by mistake if owner_type is organization
  • Future phases may need to revisit specific avoidance items with new threat model

User consent copy: Rig Relay does not request administration, secrets, actions, workflows, deployments, repository rules, or organization member permissions.

TB-GH-WEBHOOK-01

Threats:

  • Spoofed webhook with invalid signature
  • Replay attack with duplicated delivery ID
  • Oversized payload DoS
  • Malformed JSON injection
  • Information leakage via events from unauthorized repos

Controls:

  • X-Hub-Signature-256 verification with timing-safe compare
  • Delivery deduplication by delivery ID
  • Payload size cap
  • JSON parsing after signature verification
  • Repository authorization check

Required Tests:

  • test_webhook_signature_verification
  • test_webhook_signature_rejection
  • test_delivery_deduplication
  • test_payload_size_rejection
  • test_unauthorized_repo_rejection

Threats:

  • Token leakage in logs or traces

RSK-GH-KEY-01: Private Key Compromise

If the GitHub App private key is compromised, an attacker can generate JWTs, obtain installation tokens, and read/write to all installed repositories. This is the highest-value secret in the GitHub App integration.

Mitigations:

  • Private key in OS keyring, never in repo
  • File permissions 600 or stricter
  • Key reference only in config
  • Never in trace events, logs, or frontend
  • Detection test for PEM in repo
  • Key rotation procedure documented
RSK-GH-WEBHOOK-02: Webhook Secret Compromise

If the webhook secret is compromised, an attacker can forge webhook events and inject malicious data into the Rig event store.

Mitigations:

  • Webhook secret in keyring or env, never in repo
  • Secret reference only in config
  • Never in trace events or frontend
  • Signature verification on every request
RSK-GH-TOKEN-03: Installation Token Leakage

If an installation access token leaks to disk, logs, or frontend, an attacker with local access can use it to access repositories until it expires (1 hour).

Mitigations:

  • Memory-only token cache
  • Never written to disk
  • Never in trace events or frontend
  • Short expiry (1 hour, cache with 55-min TTL)
  • No long-lived token storage
RSK-GH-WRITE-04: Unauthorized Write Actions

An agent or bug could create branches, commits, or PRs without explicit user approval, violating the governed write model.

Mitigations:

  • Explicit user approval required for every write action
  • No automated write actions
  • Approval gate integration test
  • Audit trail for every write proposal
RSK-GH-CONTEXT-05: Context Poisoning via GitHub Events

Malicious or crafted GitHub event payloads (PR descriptions, commit messages, issue comments) could inject harmful context into the agent's prompt.

Mitigations:

  • GitHub payloads treated as untrusted context
  • Content sanitization
  • Context size limits
  • Source tracing
  • Repository authorization check
RSK-GH-SIZE-06: Webhook Payload DoS

Large webhook payloads (near 25 MB GitHub cap) could consume excessive memory or disk, or block the webhook processing pipeline.

Mitigations:

  • Local payload size cap (e.g., 5 MB)
  • Reject before full body read
  • Content-light event ledger (no raw payload storage)
  • Rate limiting on webhook endpoint
RSK-GH-RATE-07: GitHub API Rate Limit Exhaustion

Excessive API calls for token exchange or status posting could exhaust rate limits, degrading the integration.

Mitigations:

  • Token cache with expiry (reuse within window)
  • Exponential backoff with jitter
  • Rate limit monitoring via X-RateLimit-Remaining
  • User-facing rate limit status
RSK-GH-PERM-08: Permission Scope Creep

Over time, new features may request additional permissions without proper audit, gradually expanding the attack surface.

Mitigations:

  • Admin avoidance profile as canonical deny-list
  • Permission audit on every profile change
  • Permission diff detection on installation update
  • Release gate requiring permission justification

Open Questions

Should the webhook endpoint be a local HTTP server, or should Rig use smee.io / a tunnel for local development?

GitHub requires a publicly reachable URL for webhook delivery. Local development without a public URL needs a tunnel or webhook replay strategy.

Needed for: phase_1_webhook_setup

How should the private key be provisioned — user downloads from GitHub and provides path, or Rig guides through GitHub App creation flow?

The private key is generated by GitHub at app creation time and downloaded once. Rig needs to receive this key without the user copy-pasting raw PEM into a text field.

Needed for: phase_1_webhook_setup

Should Rig support multiple GitHub App installations across different accounts/orgs simultaneously?

A user might want to observe repos from personal account and organization. Supporting multiple installations increases complexity.

Needed for: phase_2_evidence_reporting

Should the write-approval model support time-bound or scope-bound pre-approval (e.g., 'approve all check-run postings for the next hour')?

Frequent approval prompts could degrade UX. Pre-approval with constraints could balance safety and usability.

Needed for: phase_3_governed_actions

Is the GitHub App integration required to be available in local-only mode (no internet), or can it require connectivity?

Rig Relay defaults to local-only. GitHub App integration inherently requires network access. Should Rig gracefully degrade when offline?

Needed for: phase_1_webhook_setup
