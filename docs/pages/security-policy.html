Rig Relay Security Policy v0

Security posture and expectations for the Rig Relay local governed runtime: local-only default, loopback bridge, token redaction, prompt-injection awareness, WebSocket validation, code schema trust, and mutation safety.

Rig Relay operates as a local-first governed runtime. All agent work, tool execution, trace storage, and identity management default to local-only. No data leaves the machine without explicit opt-in. Remote telemetry, cloud uploads, and external coordination are future, opt-in features.

The desktop bridge server binds to loopback (127.0.0.1) only. It serves the desktop cockpit frontend over HTTP and maintains a WebSocket control channel on the same loopback interface. No external network exposure is intended or supported.

Local auth tokens must never appear in raw form in trace events, documentation, static site output, frontend console logs, URL query strings, or report content. Token presence may be noted (present/absent) but the token value itself must be redacted at all emission boundaries. The trace endpoint must never derive from websocket_url or include token values.

  • Trace events use content-light doctrine: SHA256 hashes, no raw secrets.
  • Frontend trace breadcrumbs use field type, not event; never include token values.
  • Static documentation renderer escapes all content and redacts absolute local paths.
  • Generated HTML must not contain token-like strings or local machine paths.

  1. Only active, trusted code schemas with verified authority hashes may be used as implementation contracts.
  2. Source path must exist and source_hash must match the current file content.
  3. Untrusted, deprecated, or archive-status schemas must not be selected as authoritative context.
  4. Context packs must exclude generated HTML (docs/pages/**, **/*.html) unless a future schema explicitly authorizes static-site inspection.
  5. Schema content is reviewed; stale or tampered schemas are detected via hash mismatch.

Rig Relay acknowledges the risk of direct and indirect prompt injection through user input, repository content, web-fetched data, and tool output. Current mitigations include trust tier labeling in the context renderer, content-light trace doctrine, and tool permission gating. Formal prompt injection classifiers and content sanitization are identified as missing mitigations and deferred to a dedicated defense slice.

  • WebSocket upgrade at /ws must require authentication before any subscription or projection stream is delivered.
  • Origin validation on WebSocket upgrade handshake is expected to reduce CSWSH risk.
  • Message validation (schema enforcement, size limits, rate limiting) is identified as a missing mitigation.
  • POST /ws returns 405 Method Not Allowed. /ws is WebSocket-only.

  • Pre-existing modified, staged, or untracked files are protected. Agents must not discard or overwrite them.
  • Parallel agent lane changes are preserved; edits are additive.
  • Direct git commit and git add are blocked; agents use the checkpoint tool.
  • No git amend, force push, reset, or clean operations are permitted.

See the Rig Relay Security Threat Model v0 for a structured, machine-readable assessment of assets, trust boundaries, threats, mitigations, and release gates.

Security concerns should be raised via GitHub issues on the rig-relay repository. For sensitive findings, contact the maintainers directly. This is a local-first runtime; the primary threat surface is local agent behavior, not network-facing services.
